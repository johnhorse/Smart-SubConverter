## Problem Statement

现有节点分组完全由转换模板决定：前端 `PresetChips` 三档 → sidecar `presetTable`（`sidecar/main.go:101`）→ ACL4SSR ini 的 `[custom_proxy_group]` 段。模板只懂通用概念（地区、用途），不懂具体机场的命名——「专线」「家宽」「美国专线」这类机场特定节点无法归组。用户要么转换后手改客户端配置，要么忍着。

## What Makes This Cool

- **生态无人区**：subconverter 生态全走「生成 ini」路线（片段拼装、GitHub Actions 生成外部配置），Sub-Store 走 YAML/JS 覆写（玩机党工具）。「看到节点 → 打一个词 → 高亮确认 → 成组」的傻瓜交互没人做——引擎能力是公共商品，交互是护城河。
- **组是规则不是名单**：关键词随订阅自我更新，机场明天新增「香港专线 06」自动进组——比勾选名单类方案天生稳（勾选记住的是昨天的快照）。
- codex 冷读点出的欲望信号：用户自发追加「应该可以自主添加多个组」——价值不在「分组」，在「自主编排」。

## Constraints

- 硬约束（用户原话）：「操作一定要简单，用户只需傻瓜操作即可」——全部操作 = 打词 + 看高亮 + 一个开关。
- 零必填灵魂不可破：分组入口默认收起；未粘贴订阅时置灰；主流程一个像素不变。
- 引擎是 subconverter(Extended)，仓库零 C++——一切经外部配置文件通道（`config=`），不改引擎。
- 不向用户暴露：正则、组类型术语、测速 URL、重叠语义解释。

## Premises

1. 痛点真实但非致命（用户可手改客户端配置兜底），排在 TLS 之后做。
2. v1 只做页内自助；不做组编辑（改组 = 重新生成短链）；不做组间互斥/嵌套。
3. 壳层四件套现成，新代码 = 接线：preview 管道已有全部节点 URI（`twoStageConvert` 返回 `uris`，差暴露名字）、store 已有短链 SQLite（差存分组意图）、snapshot+改写器已验证本地 ini 可行（差派生）、/s/ 每次转换带 `config=`（差指向派生 ini）。
4. 引擎行为以闸门实测钉死，不猜：`[custom_proxy_group]` 行格式 \`组名\`类型\`内容\`；select/url-test 支持；正则零命中的组退化为仅含 direct（tindy2013/subconverter#23，UI 端零命中不成组挡掉）；一节点进多组是原生语义，v1 接受重叠；**关键词按字面量处理**——派生写入内容位前对正则元字符逐个转义，保证 UI 计数与引擎组成员语义一致（元字符案例进闸门与单测，节点名常含 `.`，不转义必分叉）。
5. 傻瓜落点：入口默认收起；打词+高亮+计数 = 全部操作；每组一个「自动选最快」开关默认关；正则/类型/测速 URL 一概不暴露。
6. 模板变化安全：分组意图独立存储，每次转换时从当前生效快照派生 ini（不写死进快照文件）；自定义组不引用模板内部组名（不嵌套进 🚀 节点选择 等），上游改组不受影响。现有机制（`refreshOnce` 每日刷新、逐文件 last-known-good、`rewriteINI` 每次重做、校验不过不切换）已把「模板会变」驯化为一等公民事件。
7. 分发零新增：随现有 docker 镜像（Docker Hub 主源），升级 = 拉新镜像。

## Cross-Model Perspective

codex 冷读（deepseek-v4-pro，read-only，2026-10-27，全文已呈用户）：

- **最酷版本**：零输入自动分组——preview 探测的节点名顺带聚类，前端直接弹「识别到 3 组：专线(12)·家宽(5)·美国专线(3)」一键全收，打词降级为兜底。
- **关键洞察**：「应该可以自主添加多个组」是四个选项之外的自发追加，是欲望的最强信号。
- **免费 50%**：生成 ini 路线（社区全量验证）；mihomo `proxy-groups.filter` 仅作行为 oracle 参照（我们的引擎是 subconverter，非可复用组件——采纳时降级处理）。
- **周末版**：关键词端到端最薄切片 + 派生闸门测试（断言行格式与零命中→仅 DIRECT）。
- Recommendation: 先做「关键词→组」端到端最薄切片，零输入自动建议推 v1.1。

处置：切片排序全盘采纳；聚类建议记入 v1.1 路线图；mihomo 降级为语义参照。7 条前提无一被挑战。

## Approaches Considered

### Approach A: 最薄切片——每次拉取即时派生（minimal viable）✅ 已选

前端分组面板 → 组意图 JSON 随短链入 SQLite → 客户端每次拉 /s/ 时，sidecar 从当前生效快照即时拼派生 ini 喂引擎。无缓存、派生函数无状态。Effort S；Risk Low（唯一中风险 = 引擎行格式假设，闸门实测兜底）。Pros：纯接线、无缓存失效、每次天然最新快照。Cons：每次拉取毫秒级冗余 IO（个人部署无感）。

### Approach B: 派生层入快照管理器（ideal architecture）

派生作为 snapshotManager 一等公民「用户覆盖层」：派生 ini 按 preset × 组意图哈希 × 快照代缓存落盘，快照刷新联动重生成 + 复用校验不过不切换防护。Effort M；Risk Med。Pros：拉取零额外工作、校验覆盖组段、组编辑地基。Cons：缓存失效状态机，v1 量级用不上，押注未实测假设。

### Approach C: 分组是探测副产品（creative/lateral，codex 最酷版）

preview 探测节点名顺带词库聚类，前端直接建议组一键全收，打词降级兜底。Effort M-L；Risk Med（聚类质量决定体验）。Pros：傻瓜天花板、零额外网络往返。Cons：词库维护成本、猜错添乱。

## Recommended Approach

**A**，用户明确指示 **C 记为 v1.1 路线图**、B 等量级需要再补。理由：纯接线、最危险假设（安全派生 + 引擎行格式）最先实测，错了返工只返这一层。

**线框（已用户批准）**：`wireframe-custom-groups.png`（本目录，随文档入库）——两屏：①默认态（主流程不变 + 收起的虚线分组入口）；②展开态 money screen（打词「专线」→「已命中 12」→ 命中项加粗高亮/未命中降灰 → 组 chips ×计数 + 每组「自动选最快」开关 + ＋添加分组）。埋在线框里的决策：未粘贴订阅入口置灰；「机场新增同类节点会自动进组」是唯一解释文案；重叠不解释（引擎原生）。

**技术形态（四件套接线）**：

- 前端：GroupPanel 组件（收起入口 → 展开面板）；preview 返回节点名列表；防抖 substring 匹配（非正则，与引擎字面量语义一致——转义在派生侧做，见前提 4）+ 高亮 + 计数；组意图 JSON 随转换请求提交。**补/剔个别节点记入 v1.1**（与已批准线框及「打词 + 看高亮 + 一个开关」的傻瓜口径对齐；届时契约规定每组 include/exclude 名单 schema 与对应派生字段，转义策略与前提 4 同一）。
- sidecar：store 短链表加 groups JSON 列；preview 暴露节点名（现成 uris 直接透出）；/s/ 拉取时从当前生效快照 ini 派生——读快照 → 追加 `[custom_proxy_group]` 行（select：\`组名\`select\`转义后关键词\`；开关开：\`组名\`url-test\`转义后关键词\`…）→ 写 DATA_DIR 派生文件（引擎硬限 /base，DATA_DIR=/base/data 在树内）→ `config=` 指向。**创建期零命中不成组（UI 挡）；拉取期关键词失效（订阅更新后不再命中）按引擎原生退化——组以仅含 DIRECT 形态出现在客户端，契约记录该可见形态，v1 不做拉取期重评**（快照 ini 不含订阅节点名，无状态拼接在拉取期无从判定命中）。
- 闸门实测（开工绿灯）：本机起 Extended 引擎，喂三档模板本地化 ini + 追加行（select / url-test / 零命中组各一），断言输出配置组形态符合预期、零命中组仅含 DIRECT，并加一例含正则元字符的关键词（如「IEPL 1.0」）断言 UI 命中数 == 引擎组成员数。
- 契约先行（项目传统）：docs/api-contract 增量——preview nodes 字段、短链 groups 存储、派生语义、零命中行为。

## Reviewer Concerns

No blocking findings remain. The 6 open minor finding(s) below are recorded for the user, not fixed.

### R3-1 — clarity (minor)

**Problem**

> 闸门断言仍未逐条钉死：主体仍是「断言输出配置组形态符合预期、零命中组仅含 DIRECT」。尤其「向已有 [custom_proxy_group] 段的模板 ini 追加行时，模板原有组是否全部完好保留（ini 重复段是合并还是遮蔽）」仍未列为准出条件，而追加派生机制成立与否直接系于此。

**Remedy**

> 闸门预期写成可核对清单：select / url-test / 零命中 / 元字符四例各自的期望组形态 + 模板原有组逐组点名仍在输出中 + 零命中组仅含 DIRECT。

### R3-2 — clarity (minor)

**Problem**

> 撞名行为仍留在 Open Questions（「组名与模板已有组撞名时引擎行为？（闸门定；UI 侧暂不特殊处理，实测后补契约文档）」），而单测清单仍列「撞名兜底」——要测的兜底行为仍无定义；用户自建两个同名组的行为也未规定。

**Remedy**

> 定义撞名兜底的具体行为（如派生时自动加后缀改名、或跳过该组），UI 侧至少禁止同名组重复创建；闸门实测只决定是否需要更强处理，不替代这个定义。

### R3-3 — clarity (minor)

**Problem**

> 组名/关键词的输入清洗仍缺失：组名或关键词含反引号或换行会直接破坏 ini 行格式 `组名`类型`内容`（反引号不是正则元字符，前提 4 的转义不覆盖它），空名、超长名也未约束。

**Remedy**

> 契约规定输入校验/归一化规则（禁反引号与控制字符、非空、长度上限），派生函数单测加对应用例。

### R3-4 — feasibility (minor)

**Problem**

> 「preview 暴露节点名（现成 uris 直接透出）」仍低估取名字的工作量：不同 scheme 的 URI 里名字位置不同（vmess 是 base64 JSON 的 ps/name 字段、ss/trojan 是 URL-encoded fragment），需按 scheme 解析，不是「直接透出」。

**Remedy**

> 技术形态与契约里如实写为「按 scheme 解析 URI 提取节点名」，并给解析步骤留单测（至少覆盖 vmess 与 ss 两类）。

### R3-5 — clarity (minor)

**Problem**

> QX 两段式若闸门发现 stage2 不保留追加组，产品行为仍未预先决定：QX 短链用户配了组会静默无组，还是按 target 隐藏/禁用分组入口，或契约声明仅 Clash 系生效——三选一仍未定，闸门出结果后容易卡住实现。

**Remedy**

> 预先定好 contingency（推荐：闸门证伪则按 target 在 UI 隐藏分组入口并在契约记录限制），闸门结果只负责触发执行哪一支。

### R3-6 — clarity (minor)

**Problem**

> 本轮新改的单测条目把「拉取期零命中组以仅含 DIRECT 形态写入产物」列为派生函数单测，但派生按设计是无状态拼接（sidecar 条目自述「快照 ini 不含订阅节点名，无状态拼接在拉取期无从判定命中」）：派生层区分不了命中与零命中，「仅含 DIRECT」形态也只在引擎转换产物中出现、从不写进派生 ini——该断言在派生单测层不可实现，照条目写测试会卡住或被迫改口径（DIRECT-only 形态断言冒烟条目已覆盖）。

**Remedy**

> 单测条目改成派生层可断言的口径——「组行无条件写入派生 ini（不因关键词命中与否变化）」；DIRECT-only 形态断言留在冒烟/闸门层，不重复进派生单测清单。

### 引擎行为意外发现（与设计假设不符或实现需注意）

1. **`config=` 只认 http URL**：`/base/...` 与 `file:///...` 均被当 opaque URL fetch → 400「external configuration could not be loaded」（premise 8「config= 指向树内绝对路径」在当前 latest 引擎不成立）。产品路径不受影响（sidecar 的 configURL 一直是回环 http URL 形态），但 **T5 派生实现必须是「写 DATA_DIR 文件 → 回环 serve URL」**，不能直接传路径。旧记忆「引擎本地路径硬限 /base」实指 ini 内 ruleset= 行——本地绝对路径工作正常（引擎直读文件、零网络，实测验证）。
2. **不带 config 的 /sub 会加载引擎默认 external config（testingcf.jsdelivr.net，外网依赖）**：网络抖动时同款 400。实验脚本与产品调用应始终显式带 config。
3. **http 订阅 URL → proxy-provider 模式（节点不内联）**：要看具体节点名/组成员必须两段式 mixed 展开——与产品 clash/QX 两段式一致，闸门全部例按此路径跑（也再次佐证 v1.4.0 两段式设计的必要性）。
4. `/version` 在此镜像返回 HTML 首页而非 JSON；就绪探测应改用 /sub 响应判活。
5. 同名 `custom_proxy_group=` 多行时引擎取**先出现**的定义（实测：插在模板块后 → 模板胜出、追加被吞）；「追加在前是否反吞模板组」未测（两种插入位均在模板块后，无必要）。
